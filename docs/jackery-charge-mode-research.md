# Jackery 充電モード変更の調査

調査日：2026-11-04。対象は本プロジェクトで利用する Jackery 1000 New。
これは調査メモである。実装した仕様は docs/07-control-logic.md §7.10 と docs/08-switchbot-api.md §8.4 を参照。

## 結論

充電速度を変更する MQTT コマンドの公開実装・解析資料が見つかった。
設定済み機器の HTTP 応答にも対応する `cs` と `sfc` が存在する。
したがって実装する根拠はあるが、本機での書き込み成功は未検証。
今回実行した実機アクセスは既存スクリプトによる状態取得のみで、変更コマンドは送信していない。

## 公開資料で確認できたこと

[socketry のプロトコル解析資料](https://github.com/jlopez/socketry/blob/main/docs/protocol.md)
は Android v1.0.7 / iOS v1.2.0 の解析に基づき、次の操作を記載している。

| 操作 | actionId | body | 意味 |
|---|---|---|---|
| 高速充電／静かな充電の切り替え | 10 | `{"cs": 0}` / `{"cs": 1}` | 0=fast、1=mute |
| 超急速充電の切り替え | 13 | `{"sfc": 0}` / `{"sfc": 1}` | 無効／有効 |

`cs` と `sfc` は別項目。両者の組み合わせや優先順位、機種ごとの対応は実機確認が必要。
アプリ上の日本語名称との対応も確認する。

通信先は `emqx.jackeryapp.com:8883`（MQTT over TLS）。
送信先トピックは `hb/app/{userId}/command`、QoS は 1。
ログイン応答の `userId` / `mqttPassWord` とログイン時の端末 ID を使って認証する。
認証情報や実機のシリアル番号はこのメモには保存しない。

静かな充電モードに変更するメッセージの構造例（未送信）：

```json
{
  "deviceSn": "<対象機器のシリアル番号>",
  "id": 1700000000000,
  "version": 0,
  "messageType": "DevicePropertyChange",
  "actionId": 10,
  "timestamp": 1700000000000,
  "body": {"cs": 1}
}
```

日時フィールドは送信時のミリ秒時刻を使う。
ブローカーの受領応答だけでは機器への適用を確認できない。
実装時は対象機器・対象プロパティの通知と HTTP 再取得値を照合する。

[socketry のクライアント実装](https://github.com/jlopez/socketry/blob/main/src/socketry/client.py)
にもプロパティ変更と応答待機がある。
TLS 用の Jackery CA は[定数ファイル](https://github.com/jlopez/socketry/blob/main/src/socketry/_constants.py)に含まれる。
現行クライアントはログイン時に HTTP トークンだけを保持するため、MQTT 認証情報の保持と通信処理の追加が必要。
socketry のログイン暗号化手順は現行実装と異なるため、そのまま置き換えず個別に評価する。

独立した別の実装である
[Private Jack の BLE コマンド生成処理](https://github.com/porcupin26/private_jack/blob/main/custom_components/private_jack/lib/commands.py)
でも `actionId=10` / `cs` と `actionId=13` / `sfc` の対応が一致する。
ただし、BLE の一致は本機のクラウド操作成功を保証しない。
同実装には `cs=2`（custom）もあるが、今回の検証候補は 0 / 1 に限定する。

## 実機の読み取り結果

既存の `.venv/bin/python scripts/jackery_check.py raw` で以下を確認した。
これはクラウドが返した一時点の値であり、アプリ表示との照合は未実施。

| 項目 | 取得値 | 公開資料に基づく解釈 |
|---|---|---|
| `cs` | 0 | fast（高速側、静かな充電ではない） |
| `sfc` | 0 | 超急速充電は無効 |
| `rb` | 100 | 残量 100% |
| `ip` / `acip` | 0 / 0 | 入力電力 0 W |

満充電・入力 0 W のため、この状態で設定値だけを変更しても充電電力の変化は評価できない。

## 未確認事項と次の検証

1. アプリの現在の充電速度表示と `cs=0` / `sfc=0` が一致するか確認する。
2. 設定済みアカウントの共有権限を確認する。socketry の解析では共有の `level=2` は操作可能、`level=3` は読み取り専用とされているが、本環境では未確認。
3. MQTT の認証・TLS 接続・対象機器の通知受信を検証する。
4. 書き込みを検証するときは変更前の値を記録し、まず `cs` の高速充電→静かな充電→高速充電を試す。対象機器の通知・HTTP 再取得・アプリ表示を照合し、元の状態への復帰も確認する。
5. 入力電力も評価する場合は満充電でない状態で確認する。`sfc` は別の検証対象とする。

`cs`（高速充電／静かな充電）の変更とスケジュールに合わせた自動切り替えは実装済み（docs/07-control-logic.md §7.10）。本機での書き込みは `scripts/jackery_check.py charge-mode` で確認する。`sfc` は扱わない。
今回の調査に追加パッケージのインストールは不要だった。

## 実機での検証結果（2026-11-04）

- MQTT 3.1.1 で送信すると、ブローカーの受領応答は成功するが機器には届かず、`cs` は変わらなかった（`actionId` 10／16、`deviceId` の有無のいずれも同じ）。
- MQTT 5 で同じコマンド（`actionId=10`、`{"cs": 1}`）を送ると、約1秒で機器から `cs` の通知が届き、HTTP の再取得値も一致した。
- MQTT 5 でも、受領応答が成功のまま機器に届かないことがあった（高速充電・静かな充電とも、値の形式によらない）。
- 条件を変えて連続で送った結果（MQTT 5、取得専用アカウント、スマホのアプリは終了）：

| 条件 | 成功 |
|---|---|
| 同じログイン、接続直後に送信、20秒間隔 | 3/4 |
| 送信ごとにログインし直す、接続直後に送信、20秒間隔 | 0/4 |
| 同じログイン、接続直後に送信、120秒間隔 | 2/2 |
| 接続・購読して15秒待ってから送信（初回はログイン直後）、20秒間隔 | 3/3 |

- 接続直後の送信が捨てられることがあり、ログインし直した直後は特に届かない。接続してから待つと届く。値の形式（数値の 1、文字列の "0"）や送信間隔は結果に影響しなかった。
- アプリ操作時の機器からの通知は `actionId=16` で届く。これは機器側の報告の番号で、送信するコマンドの `actionId` は 10 でよい。
- 共有を受けた取得専用アカウント（共有の `level=2`）から変更できた。
