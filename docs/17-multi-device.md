# 複数機器の制御

> **状態：仕様確定（2026-11-05）。Phase 9（機器の登録）・Phase 10（複数機器の制御）は実装済み、Phase 11〜12 は未実装（docs/15-roadmap.md）。** 決定事項は §17.14。各仕様書（§17.12）には本書を参照する形で反映済み。複数機器に関する詳細は本書を正とする。

## 17.1 目的と範囲

現在は環境変数で指定した SwitchBot プラグ1台（`SWITCHBOT_DEVICE_ID`）とポータブル電源1台（`JACKERY_DEVICE_ID`）だけを扱っている。これを次のように拡張する。

| # | 要件 | 本書 |
|---|---|---|
| 1 | SwitchBot API で取得できる機器から、Web UI で選んだ任意の機器を制御対象にする（制御デバイス設定画面。左に機器一覧、右に制御対象） | §17.5 |
| 2 | スケジュールごとに制御対象の機器を複数指定する（でんき予報のスケジュールは設定画面の既定値、任意スケジュールはルールで指定し、既定値をプリセットできる） | §17.6・§17.7 |
| 3 | ポータブル電源を複数台管理する（FOSSiBOT F2400 を追加。設定画面で「＋ポータブル電源を追加」し、名前を付ける） | §17.8・§17.9 |
| 4 | 制御対象の機器を DB で管理する（名前・種別・説明。種別はマスターテーブルで管理する） | §17.4 |
| 5 | スマートプラグをポータブル電源と紐づけられるようにする | §17.2・§17.5・§17.8 |
| 6 | 残量が下限以下になったときにスケジュールを中断する動作をやめ、そのポータブル電源に紐づくプラグだけを ON にする | §17.7.3 |

**対象外**

- SwitchBot 機器の操作は ON／OFF（`turnOn` / `turnOff`）だけにする。明るさ・色・チャンネル指定などは扱わない。`toggle` は従来どおり使わない。
- ポータブル電源の操作は、残量の取得と充電モード（高速充電／静かな充電）の変更だけにする。出力の ON／OFF などは扱わない。
- でんき予報のスケジュールの生成方法（docs/07 §7.4）は変えない。

## 17.2 用語

| 用語 | 意味 |
|---|---|
| 制御機器 | 本システムが ON／OFF する SwitchBot 機器（現在のプラグミニ） |
| ポータブル電源 | 残量を取得し、充電モードを変更する蓄電池（Jackery 1000 New、FOSSiBOT F2400） |
| 給電先のポータブル電源（紐づくポータブル電源） | 制御機器に紐づけたポータブル電源。制御機器が電気を送る先で、制御機器を OFF にすると、このポータブル電源から家電へ給電される（現在の構成では、プラグミニ → Jackery の AC 入力）。1台のポータブル電源に複数の制御機器を紐づけられる。1台の制御機器に紐づけられるポータブル電源は1台まで |
| 機器（device） | 制御機器とポータブル電源をまとめた呼び方。DB の `devices` に登録したもの |

紐づけ（要件5）は残量による判定に使う。現在の安全判定（docs/07 §7.7）は「プラグを OFF にすると Jackery から給電される」ことを前提にしており、制御機器が複数になると、どの機器を OFF にするとどのポータブル電源の残量が減るのかが分からなければ、残量で ON に戻す判定ができない。

## 17.3 基本方針

- 安全方針（docs/14 §14.1）は変えない。判定・照合・記録は**機器ごと**に行う。ある機器の失敗で他の機器の制御を止めない。
- 状態の変更は従来どおりすべて Control Service を経由する。制御サイクルは1つのままにし、その中で機器ごとに処理する。
- 秘匿情報（API トークン・アカウント・パスワード）は従来どおり環境変数だけで管理する。DB に保存するのは機器 ID・名前・設定値だけにする。
- 現在の1台構成からは自動で移行し、移行直後の動作は現在と同じにする（§17.4.7）。

## 17.4 データモデル

### 17.4.1 テーブルの追加・変更の一覧

| テーブル | 区分 | 用途 |
|---|---|---|
| device_types | 追加 | 機器の種別のマスター |
| devices | 追加 | 登録した機器（制御機器・ポータブル電源の共通項目） |
| portable_power_settings | 追加 | ポータブル電源ごとの設定（容量・残量の下限など） |
| schedule_devices | 追加 | スケジュールごとの対象機器と、機器ごとの実行結果 |
| schedule_rule_devices | 追加 | 任意スケジュールのルールごとの対象機器 |
| control_logs | 変更 | `device_id` を追加 |
| system_events | 変更 | `device_id`（任意）を追加 |
| control_schedules | 変更 | 機器ごとの実行結果の列は schedule_devices へ移す（§17.4.5） |

### 17.4.2 device_types（種別マスター）

| カラム | 説明 |
|---|---|
| id | 主キー |
| vendor | メーカー（SWITCHBOT / JACKERY / FOSSIBOT） |
| code | 種別コード。SwitchBot は API の `deviceType` の値をそのまま使う（例：`Plug Mini (JP)`）。ポータブル電源は独自のコード（例：`JACKERY_1000_NEW`、`FOSSIBOT_F2400`） |
| name | 表示名（例：プラグミニ（JP）） |
| category | POWER_SWITCH（制御機器）/ PORTABLE_POWER（ポータブル電源） |
| power_control | ON／OFF の制御に対応するか（制御対象にできるのは true の種別だけ） |
| charge_mode | 充電モードの変更に対応するか（ポータブル電源のみ） |
| default_capacity_wh | 公称容量（ポータブル電源のみ。登録時の初期値） |
| source | API（SwitchBot API の `deviceType` 由来）/ CUSTOM（独自に定義） |
| note | 備考 |

(vendor, code) で一意とする。

**SwitchBot の種別の決め方：** SwitchBot API は種別の一覧を返す API を持たないが、`GET /devices` の各機器に `deviceType`（種別名の文字列）が含まれる。そこで種別コードは `deviceType` の値をそのまま使い、表示名と ON／OFF への対応は本システムで決める。マイグレーションで次の種別を初期登録する。

| code（deviceType） | 表示名 | power_control |
|---|---|---|
| Plug Mini (JP) | プラグミニ（JP） | true（実機で確認済み） |
| Plug Mini (US) | プラグミニ（US） | true |
| Plug Mini (EU) | プラグミニ（EU） | true |
| Plug | プラグ | true |
| Relay Switch 1 | リレースイッチ1 | false（実機で確認してから true にする） |
| Relay Switch 1PM | リレースイッチ1PM | false（同上） |

- 初期の対応はプラグに限る（2026-11-07 変更。現在 ON／OFF で使う機器がプラグだけのため）。リレースイッチも電源そのものを入り切りする機器だが、実機で確認するまでは非対応とし、種別マスターには登録しておく。照明（Ceiling Light・Color Bulb・Strip Light）は ON／OFF を受け付けるが、電源の切り替え用途ではないため初期は対象外とする。Bot はプレスモードでは状態を照合できないため対象外とする。Relay Switch 2PM はチャンネルを指定するコマンドのため対象外とする。
- 一覧に知らない `deviceType` が含まれていた場合は、`power_control=false`・`source=API` として自動で追加し、画面には「非対応」と表示する（制御対象にはできない）。対応を増やすときは、実機で ON／OFF と状態の照合を確かめてからマイグレーションで `power_control=true` にする。
- 実機で確認していない種別（上の表の「実機で確認済み」以外）を初めて制御対象にするときは、制御デバイス設定画面に「実機での確認が済んでいない種別です」と表示する。

### 17.4.3 devices（機器）

| カラム | 説明 |
|---|---|
| id | 主キー |
| device_type_id | 種別（device_types.id） |
| external_id | メーカー側の機器 ID（SwitchBot の `deviceId`、Jackery の `deviceId`、FOSSiBOT の機器 ID） |
| name | 名前（画面表示用。初期値は SwitchBot アプリでの名前 `deviceName`。変更できる） |
| note | 説明（任意） |
| power_source_id | 給電先のポータブル電源（devices.id。制御機器のみ。未設定可） |
| estimated_power_w | 想定平均負荷（W。制御機器のみ。推定節約額の算出に使う。未設定なら設定画面の `ESTIMATED_AVERAGE_POWER_W`） |
| active | 制御対象か（制御デバイス設定画面の右ペインにあるもの。外したものは false とし、行は残す） |
| sort_order | 表示順 |
| last_state / last_state_at | 最後に取得した状態（ON / OFF / UNKNOWN、制御機器のみ）と取得日時 |
| created_at / updated_at | 作成・更新日時 |

(device_type_id の vendor, external_id) で一意とする。

**ポータブル電源も devices に登録する（専用テーブルに分けない）。** 理由：

- 制御機器との関連（`power_source_id`）、制御履歴・イベント（`device_id`）を同じ外部キーで扱える。
- 名前・種別・説明は共通の項目で、種別マスターも共通にできる。
- ポータブル電源だけの設定は 1:1 の `portable_power_settings` に分け、制御機器の行に使わない列を増やさない。

### 17.4.4 portable_power_settings（ポータブル電源の設定）

現在は環境変数・`system_settings` の全体設定であるものを、ポータブル電源ごとに持つ。

| カラム | 説明 | 現在の設定 |
|---|---|---|
| device_id | 主キー（devices.id） | — |
| capacity_wh | 容量（Wh） | `BATTERY_CAPACITY_WH` |
| min_percent | 残量の下限（%） | `BATTERY_MIN_PERCENT` |
| efficiency | 変換効率（残量の予測・推定節約額の充電分に使う） | `ROUND_TRIP_EFFICIENCY` |
| charge_mode_enabled | 充電モードを切り替えるか（種別が対応していても切り替えたくない場合に false） | なし |
| last_percent / last_output_w / last_input_w / last_charge_mode / last_read_at | 最後に取得した残量・出力・入力・充電モードと取得日時 | なし（現在はメモリ上） |

### 17.4.5 schedule_devices（スケジュールの対象機器と実行結果）

| カラム | 説明 |
|---|---|
| id | 主キー |
| schedule_id | control_schedules.id |
| device_id | devices.id（制御機器） |
| status | 機器ごとの実行状態（PENDING / RUNNING / RETURNED / DONE / ABORTED / SKIPPED）。RETURNED は「紐づくポータブル電源の残量が下限以下のため ON に戻した（スケジュールは継続中）」（§17.7.3） |
| status_reason | 中断・未実行の理由 |
| executed_start_at / executed_end_at | 実際に OFF にした時間帯 |
| executed_saving | 実行した時間帯の推定節約額 |
| battery_start_percent / battery_end_percent | 給電先のポータブル電源の開始時・終了時の残量 |
| measured_power_w | 実行中の給電先の出力の平均 |
| power_source_id | 実行時の給電先（devices.id）。同じスケジュールで同じ給電先の機器は実測値が同じになるため、日次集計・調整の目安で1件として数えるのに使う |

(schedule_id, device_id) で一意とする。

- control_schedules の `status` は機器ごとの状態をまとめた値にする：いずれかが RUNNING または RETURNED なら RUNNING、すべて終わったら DONE（1台でも完了）／ABORTED（すべて中断）／SKIPPED（すべて未実行）。
- 終了時刻を迎えたとき、RETURNED の機器は DONE とし、`status_reason` に「残量低下のため HH:MM に ON に戻した」と残す（中断扱いにしない）。`executed_end_at` は ON に戻した時刻とする。
- `estimated_saving`（計画時）・`executed_saving` は機器ごとの合計を control_schedules にも持つ（一覧表示・日次集計の互換のため）。
- `executed_start_at` などの機器ごとの列は control_schedules から schedule_devices へ移し、control_schedules の列は削除する。

### 17.4.6 schedule_rule_devices（ルールの対象機器）

| カラム | 説明 |
|---|---|
| rule_id | schedule_rules.id |
| device_id | devices.id（制御機器） |

主キーは (rule_id, device_id)。ルールを展開するときに schedule_devices へ写す。

### 17.4.7 その他の変更と既存データの移行

- **system_settings**：`forecast_schedule_devices`（でんき予報のスケジュールの対象機器。devices.id の配列）を追加する。
- **control_logs**：`device_id` を追加する。`previous_state` / `actual_state` はその機器の状態とする。
- **daily_summaries**：全機器の合計のままにする（機器別の集計は必要になってから追加する）。
- **移行（マイグレーション＋初回起動時）**：
  1. 種別マスターを初期登録する。
  2. `SWITCHBOT_DEVICE_ID` が設定されていれば、その機器を devices に登録し（名前は API で取得できれば `deviceName`、できなければ「スマートプラグ」）、制御対象・でんき予報の対象機器にする。
  3. `JACKERY_DEVICE_ID`（空欄なら共有されている1台）を devices に登録し、現在の `BATTERY_*`・`CHARGE_MODE_*`・変換効率の値で portable_power_settings を作り、2 のプラグの給電先にする。
  4. 既存の control_schedules・schedule_rules・control_logs を 2 の機器に関連付ける（既存の実行結果の列は schedule_devices へ写す）。
  5. 移行後、`SWITCHBOT_DEVICE_ID` / `JACKERY_DEVICE_ID` は使わない（§17.11）。

## 17.5 制御デバイス設定画面

### 17.5.1 画面

新しい画面「制御機器」（`/devices`）を追加し、ヘッダーのメニューに加える。

```text
┌─ SwitchBot の機器 ─────────────┐      ┌─ 制御対象 ──────────────────────┐
│ [再取得]  最終取得 11/05 22:10 │      │ リビングのプラグ  プラグミニ（JP）│
│ □ 書斎のプラグ   プラグミニ(JP)│  →   │   給電先：Jackery 1000 New       │
│ □ 寝室のプラグ   プラグミニ(US)│  ←   │   [編集]                         │
│ ▸ 非対応の機器 3台（表示していません）│                                  │
└────────────────────────────────┘      └──────────────────────────────────┘
                                                         [保存]
```

- **左ペイン（SwitchBot の機器）**：`GET /devices` の `deviceList` のうち、制御対象になっていない、ON／OFF に対応する種別（`power_control=true`）の機器だけを表示する。クラウドサービスが無効（`enableCloudService=false`）の機器は「クラウドサービスが無効」として灰色で表示し、選択できないようにする（SwitchBot アプリで有効にすれば選べるため）。対応しない種別の機器は一覧に出さず、「非対応の機器 N台（表示していません）」とだけ表示し、開くと名前と種別を確認できるようにする。赤外線リモコン（`infraredRemoteList`）は状態を取得できないため表示しない。
- **右ペイン（制御対象）**：devices の `active=true` の制御機器を表示する。名前・種別・給電先のポータブル電源・説明を表示する。
- **移動**：左の機器を選んで「→」で右へ、右の機器を選んで「←」で左へ移す。PC ではドラッグ＆ドロップでも移せる。スマートフォンでは上下に並べ、各行の「追加」「外す」ボタンで移す。
- **保存**：「保存」で変更を確定する（それまでは DB を変えない）。保存時に §17.5.3 の検証を行い、結果を表示する。
- **編集**：右ペインの機器ごとに、名前・説明・紐づくポータブル電源（給電先。未設定可）・想定平均負荷を変更できる。紐づけの変更は、その機器が実行中のスケジュールの対象になっていない間だけ行える。右へ移したときは、名前の初期値を SwitchBot アプリでの名前にし、給電先は未設定、想定平均負荷は空欄（全体の設定値を使う）にする。

### 17.5.2 機器一覧の取得

- SwitchBot API を呼ぶのは、画面を開いたときに一覧が未取得か24時間以上前の場合と、「再取得」を押した場合だけにする（API の呼び出し上限：1日10,000回）。取得した一覧はメモリに保持する（DB には制御対象の機器だけを保存する）。
- 取得に失敗した場合は、右ペイン（DB の内容）だけを表示し、左ペインにエラーを表示する。
- 制御対象の機器が一覧に含まれなくなった場合（SwitchBot アプリから削除した場合など）は、右ペインに「SwitchBot に見つかりません」と表示する。制御サイクルでは状態を取得できない機器として扱う（§17.7.3）。

### 17.5.3 制御対象から外すとき

| 状況 | 扱い |
|---|---|
| 実行中のスケジュールの対象になっている | 外せない（「実行中のスケジュールが終わってから外してください」） |
| 本システムが OFF にしている（状態が OFF） | ON に戻してから外す（ON にできなければ外さない）。保存時に確認ダイアログを表示する |
| 開始前のスケジュール・ルール・でんき予報の対象機器に含まれる | 保存時に件数を表示して確認し、それらから外す。対象機器が0台になった開始前のスケジュールは「未実行（対象機器がありません）」とする。0台になったルールは無効にする |

外した機器は `active=false` として行を残す（制御履歴から参照するため）。もう一度右へ移したときは同じ行を `active=true` に戻す。

## 17.6 スケジュールの対象機器

### 17.6.1 指定のしかた

| スケジュール | 対象機器の決め方 |
|---|---|
| でんき予報のスケジュール | 設定画面の「でんき予報のスケジュールの対象機器」（`forecast_schedule_devices`）で生成する |
| 任意スケジュール（ルール） | ルールの登録・編集画面で選ぶ。初期状態は未選択とし、「でんき予報のスケジュールと同じ機器を選ぶ」ボタンで既定値をプリセットできる。1台以上選ばないと保存できない |
| 展開・生成したスケジュール | 運転スケジュール画面で開始前のものだけ個別に変更できる（手動変更済みとし、再生成で上書きしない） |

- でんき予報の対象機器の初期値は、移行時の機器（§17.4.7）とする。0台にした場合は、でんき予報のスケジュールを生成しない（画面に「対象機器が未設定のため生成しません」と表示する）。
- でんき予報の対象機器・ルールの対象機器の変更は、手動で変更していない開始前のスケジュールに再生成で反映する（充電モードの既定値と同じ扱い。docs/07 §7.10）。
- 選べるのは制御対象（`active=true`）の制御機器だけとする。

### 17.6.2 対象機器の上限

**1つのスケジュールの対象機器は5台までとする。** 制御対象として登録できる機器の数は制限しない。

根拠：

- SwitchBot API の呼び出し上限は1日10,000回。制御機器ごとに5分ごとの状態確認（288回/日）と、切り替えのたびに送信と照合（最大約12回）がかかる。5台でもおおむね2,000回/日に収まり、手動の再取得や再試行の余地が残る。
- 送信後の照合は3秒ごと最大5回、1回送り直すため、1台で最大30秒ほどかかる。制御サイクルは毎分のため、§17.7.2 のとおり機器ごとに並行して処理しても、台数が多いと API の同時呼び出しと遅延が増える。

上限は設定値（`MAX_DEVICES_PER_SCHEDULE`、初期値5）とし、運用しながら見直す。

### 17.6.3 時間の重なり

**スケジュール同士は、対象機器が異なっていても時間が重ならないようにする（現在の検証をそのまま使う）。**

- 現在の重なり・最低切り替え間隔の検証（docs/07 §7.6・§7.9）と、でんき予報のスケジュールが任意スケジュールを避けて生成される処理（§7.9）をそのまま使える。
- 「プラグ A は 12:00〜13:00 任意 OFF、プラグ B は同じ時間にでんき注意報で OFF」のような組み合わせはできない。このような使い方が必要になったら、重なりを機器ごとに判定する方式（§17.14 の D-3 で採らなかった案）へ拡張する。

OFF 時間の制限（最大連続 OFF 時間・1日の最大 OFF 時間）は、従来どおりスケジュールの時間で判定する。時間が重ならないため、どの機器でも1日の OFF 時間はスケジュールの合計以下になる。

## 17.7 実行

### 17.7.1 制御状態

制御状態（GRID / BATTERY / SAFE）を制御機器ごとに持つ。自動制御の停止・再開（AUTO／MANUAL）はシステム全体で1つのままにする（§17.14 の D-4）。

| 操作 | 影響 |
|---|---|
| ダッシュボードで機器を手動で ON／OFF | MANUAL へ移行する（全体）。実行中のスケジュールは全機器で中断する |
| 自動制御の停止・再開 | 全機器（従来どおり） |
| 手動 OFF の安全制御 | 機器ごと（給電先の残量で判定する） |

### 17.7.2 制御サイクル

毎分の制御サイクル（docs/07 §7.8）で、制御対象の機器ごとに要求する状態を決める。

1. 機器ごとに、その機器を対象に含む現在の有効なスケジュールを探す（時間が重ならないため、多くても1つ）。
2. スケジュールがあれば、その機器について安全判定（§17.7.3）を行い、通れば OFF（任意 ON なら ON）を要求する。通らなければその機器だけ中断する（他の機器は続ける）。
3. スケジュールがなく OFF 中なら ON に戻す。
4. 送信と照合（docs/08 §8.3）は機器ごとに並行して行う（同時に処理するのは最大5台）。照合できなかった機器だけを「状態不明」とし、その機器は ON への初期化のみ要求する。
5. 「失敗した要求は5分間繰り返さない」は機器ごとに判定する。

### 17.7.3 安全判定

従来の判定（docs/07 §7.5・§7.7）を、制御機器ごとに**給電先のポータブル電源**の残量で行う。

**残量が下限以下になったとき（要件6）：** 現在は、残量が下限以下（予測を含む）になるとスケジュールを中断（ABORTED）し、プラグを ON に戻している（開始時なら開始しない）。これを次のように変える。

| 場面 | 現在 | 変更後 |
|---|---|---|
| 実行中（OFF 中）に残量が下限以下・下回る予測 | スケジュールを中断し、プラグを ON に戻す | そのポータブル電源に紐づく制御機器だけを ON に戻し、`schedule_devices.status` を RETURNED にする。スケジュールは中断せず、他の機器は OFF を続ける |
| 開始時に残量が下限以下・下回る予測 | スケジュールを中断し、OFF にしない | 紐づく制御機器だけ OFF にせず RETURNED にする。他の機器は開始する |
| 紐づく機器がすべて RETURNED になった | — | スケジュールは終了時刻まで実行中のまま残し、終了時刻に DONE とする |

- RETURNED にした機器は、そのスケジュールの終了まで OFF に戻さない（§17.14 の D-9）。残量が高い単価の時間帯に系統から充電されて回復しても、同じ時間帯に放電すれば節約にならず、変換ロスの分だけ損になるため。切り替えの往復も避けられる。
- 制御履歴には SAFETY として記録する（理由：「〇〇（ポータブル電源名）の残量が下限以下のため ON に戻す」）。ON に戻せなかった場合（失敗・未確認）は、従来どおり異常表示し、5分後に再試行する。
- 間隔0で続く次のスケジュールでも、残量が下限以下のままなら、その機器は開始時に RETURNED になる。
- 残量以外の安全判定（OFF 時間の制限・自動 OFF の許可時間の超過）で止める場合は、従来どおりスケジュール全体を中断する（ABORTED。要件6は残量の判定だけを対象とする）。実装では判定を機器ごとに行うため、でんき注意報・任意 OFF ではすべての機器が同時に中断する（スケジュール全体の中断と同じ）。でんき警報で、残量を取得できる機器とできない機器が混在する場合は、制限に達した（残量を取得できない）機器だけを中断し、残量を取得できる機器は続ける。
- 手動 OFF（MANUAL）中の残量による安全制御は、紐づく制御機器だけを ON に戻す（他の手動 OFF の機器はそのまま）。

| 給電先のポータブル電源 | 判定 |
|---|---|
| 設定済みで残量を取得できる | そのポータブル電源の残量・出力・設定（下限・容量・効率）で判定する（警報は制限を超えてよい） |
| 設定済みで残量を取得できない | 残量を取得できない場合と同じく、OFF 時間の制限を適用する（警報にも適用する） |
| 未設定 | 残量を取得できない場合と同じ扱いとする（常に OFF 時間の制限を適用する） |

- 複数の制御機器が同じポータブル電源に給電している場合、出力（消費電力）はポータブル電源の値をそのまま使う（家電の消費電力の合計を表すため）。残量が下限を下回る予測になったら、そのポータブル電源に紐づくすべての制御機器を ON に戻す（RETURNED）。
- 残量の取得は、OFF 中の機器の給電先になっているポータブル電源だけ5分ごとに行う（同じポータブル電源は1回だけ取得する）。
- 機器の状態を取得できない（SwitchBot に見つからない・オフライン）場合は、その機器に OFF を要求しない。

### 17.7.4 起動時

機器ごとに状態を取得して引き継ぐ（docs/09 §9.2）。取得できない機器だけ ON への初期化を要求する。

### 17.7.5 推定節約額

推定節約額（docs/07 §7.2）は対象機器ごとに算出して合計する。

```text
機器ごとの推定節約額 = OFF 時間帯の電源単価 × 想定平均負荷(機器) × OFF 時間
                     − 最安の電源単価 × 想定平均負荷(機器) × OFF 時間 ÷ 変換効率(給電先)
```

想定平均負荷は機器の `estimated_power_w`（未設定なら全体の設定値）、変換効率は給電先のポータブル電源の値（未設定なら全体の設定値）を使う。

## 17.8 ポータブル電源の複数管理

### 17.8.1 認証情報と機器の登録

- アカウント・パスワードは従来どおり環境変数で、**メーカーごとに1つ**設定する（`JACKERY_ACCOUNT` / `JACKERY_PASSWORD`、FOSSiBOT は §17.9 の調査結果で決める）。複数台は、同じアカウントに共有して扱う（Jackery は取得専用アカウントに共有する。docs/08 §8.4）。
- 機器の選択は画面で行う。メーカーのアカウントで取得した機器一覧から選んで登録する（現在の `JACKERY_DEVICE_ID` は使わない）。

### 17.8.2 設定画面

現在「ポータブル電源」「充電モード」に分かれている設定を、「ポータブル電源」にまとめる。ポータブル電源ごとに次のブロックを表示する。

```text
ポータブル電源
  充電モードの既定値（でんき予報のスケジュール）：開始時 [静かな充電] 終了時 [高速充電]
┌─ Jackery 1000 New ─────────────────────────────── [削除] ┐
│ 名前        [Jackery 1000 New      ]                     │
│ 機器        Jackery / 1000 New（ID: ...1234）             │
│ 容量        [1070] Wh    残量の下限 [5] %  変換効率 [85] %│
│ 充電モード  [✓] スケジュールに合わせて切り替える          │
│ 紐づくプラグ [✓] リビングのプラグ  [ ] 書斎のプラグ        │
│ 説明        [                      ]                     │
│ 直近30日の実測：平均消費電力 142W・推定効率 83%           │
└───────────────────────────────────────────────────────────┘
[＋ ポータブル電源を追加]
```

- 充電モードの既定値（でんき予報のスケジュールの開始時・終了時）は全体で1つとし、ブロックの上に表示する（§17.8.3）。
- 「＋ポータブル電源を追加」を押すと、同じ内容の空のブロックを下に追加する。ブロックではまずメーカーを選び、そのアカウントの機器一覧（未登録のもの）から機器を選ぶ。容量は種別の公称容量、その他は全体の設定値を初期値にする。
- 名前は必須とし、ポータブル電源同士で重複させない。
- 各ブロックに「紐づくプラグ」として、制御対象の制御機器から複数選べる欄を設ける（制御デバイス設定画面の紐づけと同じ値。どちらで変更してもよい）。すでに別のポータブル電源に紐づいているプラグを選ぶと、紐づけ先を移す確認を表示する。
- 「削除」は、制御機器の給電先になっている場合は確認ダイアログで件数を表示し、それらの給電先を未設定に戻してから削除する（`active=false`）。OFF 中の制御機器の給電先は削除できない。
- メーカーのアカウントが未設定の場合は、そのメーカーを選択肢に出さない（「環境変数で設定してください」と表示する）。

### 17.8.3 充電モード

- スケジュールの開始時・終了時の充電モード（docs/07 §7.10）は、**スケジュールの対象機器の給電先になっているポータブル電源**（`charge_mode_enabled=true` のもの）に送る。
- スケジュールの `charge_mode_start` / `charge_mode_end` はスケジュールに1つのまま（給電先のすべてに同じモードを送る）とする。でんき予報のスケジュールの既定値は、ポータブル電源ごとの既定値ではなく、全体の既定値（現在の `CHARGE_MODE_START` / `CHARGE_MODE_END`）を使う（§17.14 の D-6）。
- 残量の下限で紐づく機器を ON に戻した場合（§17.7.3）は、そのポータブル電源に紐づく対象機器がすべて ON に戻った時点で、スケジュールの終了時の設定に切り替える（§17.14 の D-10）。
- 失敗・照合・再試行・Dry Run の扱いはポータブル電源ごとに従来どおり行う。
- ダッシュボードの手動変更はポータブル電源ごとに行う。

## 17.9 FOSSiBOT F2400 の調査

### 17.9.1 現時点で分かっていること（2026-11 時点の公開情報）

- 公式 API は公開されていない。アプリは BrightEMS（メーカーは SYDPOWER。F2400 は SYDPOWER N052 と同じハードウェア）。
- Home Assistant の非公式統合 [ha-fossibot](https://github.com/iamslan/ha-fossibot) が F2400 に対応している。
  - 1.x は SYDPOWER のクラウド経由。2.0 以降は**自前の MQTT ブローカー**経由に変わった。
  - 2.0 以降は、BrightEMS アプリ（1.6.0 以降）の「ローカル MQTT ブローカー設定」で、機器の接続先を自前のブローカーにする必要がある。設定できるのは最初に機器を登録したアカウント（マスターアカウント）だけ。機器一覧の取得には BrightEMS の API トークンを使う。
  - 読み取れる値：残量（拡張バッテリーを含む）、入力（AC・DC・USB-C・合計）、出力（合計・AC・ポートごと）、充電中かどうかなど。
  - 変更できる値：AC 静音充電（AC Silent Charging）、AC 充電速度（1〜5段階）、出力の ON／OFF、放電の下限、充電の上限など。
- F2400 での利用報告には、ブローカーの認証で接続できないという報告がある（[Home Assistant コミュニティ](https://community.home-assistant.io/t/fossibot-integration/796411)）。
- ほかに、ESP32 を使って Bluetooth で直接つなぐ方法（[ESP-FBot](https://devices.esphome.io/devices/ESP-FBot/)）もある。

### 17.9.2 方式の候補

| 案 | 方式 | 長所 | 短所 |
|---|---|---|---|
| A | クラウド API（ha-fossibot 1.x と同じ方式） | 追加の機器が要らない。Jackery と同じ構成 | 非公式で、作者がクラウド方式をやめている（使えなくなっている可能性がある）。ログインの同時実行の制限は未確認 |
| B | 自前の MQTT ブローカー（ha-fossibot 2.0 以降と同じ方式） | 宅内で完結し、クラウドの変更の影響を受けにくい | ブローカー（Mosquitto など）の追加が必要。機器から LAN 経由でブローカーに届く必要がある（現在の WSL2 の Docker は localhost にだけ公開している）。BrightEMS アプリのクラウド機能が使えなくなるかは未確認 |
| C | Bluetooth（ESP32 経由） | クラウドに依存しない | ESP32 の用意と設置が必要。本システムの構成から外れる |

案 A を最初に確かめ、使えなければ案 B を確かめる。案 C は本書の範囲外とする。

### 17.9.3 調査項目と採用の条件

`scripts/fossibot_check.py`（読み取り専用。`docs/jackery-charge-mode-research.md` と同じく経緯を `docs/fossibot-research.md` に残す）で次を確かめる。

| # | 確認すること | 採用の条件 |
|---|---|---|
| 1 | ログインと機器一覧の取得（案 A）、またはブローカーへの接続（案 B） | 環境変数の認証情報だけで取得できる |
| 2 | 同時ログインの制限（スマホのアプリがログアウトされるか） | 取得専用のアカウント（共有）で運用できる |
| 3 | 残量（%）・出力（W）・入力（W）の取得 | 5分ごとの取得で安定して取れる |
| 4 | AC 静音充電の切り替えと、切り替え後の状態の再取得 | 再取得で照合できる（照合できない場合は充電モードを対象外とし、残量の取得だけで採用する） |
| 5 | 拡張バッテリーをつないだときの残量の扱い | 本体＋拡張の合計の残量を判定に使えるか決める |

1〜3 を満たせば採用する（残量の取得だけでも、安全判定に使えるため価値がある）。満たさない場合は FOSSiBOT を対象外とし、本書の §17.9.4 は実装しない。

### 17.9.4 採用した場合の仕様

- `app/clients/fossibot.py` を追加し、Jackery と同じ操作（機器一覧・状態の取得・充電モードの変更）を提供する。
- ポータブル電源のクライアントを共通の形（`app/clients/portable_power.py` の Protocol：`list_devices()`・`read(device)`・`set_charge_mode(device, mode)`）に揃え、BatteryMonitor はメーカーを意識せずに使う。
- 充電モードの対応：静かな充電（SILENT）＝ AC 静音充電を ON、高速充電（FAST）＝ AC 静音充電を OFF とする。AC 充電速度（1〜5段階）は扱わない。
- 種別マスターに `FOSSIBOT_F2400`（公称容量 2048Wh）を追加する。
- 環境変数は案に応じて追加する（例：案 A は `FOSSIBOT_ACCOUNT` / `FOSSIBOT_PASSWORD`、案 B は `FOSSIBOT_API_TOKEN` / `FOSSIBOT_MQTT_HOST` / `FOSSIBOT_MQTT_PORT` と docker-compose へのブローカーの追加）。

| 11：複数のポータブル電源 | ポータブル電源の画面での登録（§17.8）、給電先ごとの残量判定・充電モード、クライアントの共通化 | Jackery を画面から登録し、給電先ごとに判定できる |
| 12：FOSSiBOT | 調査（§17.9.3）。採用の条件を満たせば実装（§17.9.4） | 調査結果を記録し、採用時は F2400 の残量で判定できる |

Phase 12 の調査は Phase 9〜11 と並行して始めてよい（調査の結果が §17.8 の環境変数・画面に影響するため、Phase 11 より前に終えるのが望ましい）。

## 17.14 決定事項

2026-11-05 にすべて次のとおり決定した。

| # | 事項 | 決定 | 採らなかった案 |
|---|---|---|---|
| D-1 | 給電先のポータブル電源（§17.2） | プラグとポータブル電源を紐づける（要件5） | — |
| D-2 | 1つのスケジュールの対象機器の上限 | 5台（`MAX_DEVICES_PER_SCHEDULE` で変更可） | 3台／上限なし（API の呼び出し回数のみ監視） |
| D-3 | 対象機器が異なるスケジュールの時間の重なり | 許さない（現在の検証を使う） | 機器ごとに重なりを判定する（でんき予報のスケジュールを機器ごとに分けて生成する必要があり、変更が大きい） |
| D-4 | 手動操作による MANUAL の範囲 | 全体（現在と同じ。機器を1台手動操作すると自動制御全体が止まる） | 機器ごと（手動操作した機器だけ自動制御を止める。状態の持ち方と画面が複雑になる） |
| D-5 | ポータブル電源の管理方法 | devices に統合し、設定は portable_power_settings に分ける（§17.4.3） | ポータブル電源専用のテーブルにする |
| D-6 | でんき予報のスケジュールの充電モードの既定値 | 全体で1つ（現在と同じ） | ポータブル電源ごと（同じスケジュールでポータブル電源ごとに違うモードを送る） |
| D-7 | 初期の対応種別 | プラグのみ（§17.4.2。2026-11-07 にリレースイッチを外した） | リレースイッチ・照明なども含める |
| D-8 | 機器ごとの日次集計 | 当面は全体の合計のみ | 機器別の集計テーブルを追加する |
| D-9 | 残量低下で ON に戻した機器（RETURNED）を、同じスケジュール中に OFF に戻すか | 戻さない（§17.7.3） | 残量が「下限＋復帰幅（例：20%）」以上に回復し、最低切り替え間隔を過ぎたら OFF に戻す（高い単価で充電した電気を同じ時間帯に使うことになり、節約にならない） |
| D-10 | 残量低下で ON に戻したときの充電モード | そのポータブル電源に紐づく機器がすべて ON に戻ったら、終了時の設定（初期値は高速充電）に切り替える | スケジュールの終了時刻まで変えない（高い単価の時間帯に静かな充電のまま少しずつ充電する） |
